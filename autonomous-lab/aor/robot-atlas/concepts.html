从课程术语读懂本地机器人

课程原讲义未附在任务中；这里按用户列出的术语作中文对照，不声称复述某页课程内容。具体数值见 知识入口，MuJoCo 机制参考官方 Overview 与 Computation。

先用人话理解这三张表

把仿真想成管理员在同一张场地里照看机器人、球和桌子。它至少需要记录：

记录什么存数据的数组要准备多少个格子
此刻各物体在哪里、朝向哪里，各关节弯了多少qposnq
此刻它们移动、转动或关节变化得多快qvelnv
此刻要给各驱动通道什么命令ctrlnu

n 可以理解为“数量”。比如 nq=21 表示需要 21 个数记录构型；qpos 才装着这 21 个数当前各是多少。已加载的模型不变时，表长通常不变；机器人移动时变化的是表里的数值。

拿 Duck 举例：身体内部有 14 个转动关节，各用一个角度记录。但 Duck 整体也会走、转身甚至摔倒，所以还需记录它整台身体的位置和朝向。这部分用 3 个位置数和 4 个朝向数，于是 nq=14+3+4=21。这里朝向用的四元数是一种存储方法，先记住它需要 4 个数即可。

速度表中，14 个关节各有一个转动速度；整台 Duck 另有 3 个平移速度和 3 个转动速度，于是 nv=14+3+3=20。控制表有 14 个关节驱动通道，所以 nu=14。没有额外的“自由基座电机”负责把整台 Duck 直接搬过去。

为什么机器人、球会一起统计

这三个数量属于一个加载后的 MjModel。如果把 Duck、Stretch 和球放进同一个模型，MuJoCo 就把它们的状态统一放进大数组，每个对象占自己的几段；它们仍然可以由不同控制器控制。统一记录是为了同一次物理步进能处理相互碰撞、夹持和受力，不表示多个机器人的控制策略合并成一个。

场景里的 qpos： [Duck 的身体和关节 | 球的位置和朝向 | Stretch 的身体和关节 | 第二个球…]
场景里的 ctrl： [Duck 的驱动命令   | Stretch 的驱动命令]
                                    球没有驱动命令

这是分段存放的示意，实际顺序由编译模型决定；程序应通过名称与地址找到所属段，不能假定所有模型采用相同下标。物理球虽不是“智能体”，仍有状态：本地球可以自由移动和旋转，所以每个新增 7 qpos + 6 qvel，但不新增 ctrl。球被踢动来自碰撞，不需要给球装一个控制通道。

固定地面、固定桌子通常不增加 nq/nv/nu，但会增加碰撞几何等模型内容。可移动桌子若有自由关节，就要增加状态。碰撞发生、夹爪抓住球，并不会自动把数组变长；mj_step 是把整个场景向前推进一小步，再更新已有数组中的数值。

所以应同时展示“单个机器人是什么结构”和“这次加载了哪些对象、整个场景有多大的数组”。不能只给组合总数而让读者猜每台机器人有多少关节。结构数量与连接关系见 STRUCTURE.md。

三种“模型”先分开

名称解决的问题本地例子
机器人描述模型身体如何连接、质量/惯性多大、在哪里碰撞、关节怎么动Stretch stretch.xml、Duck robot_groundcontact.xml、H1 h1.usd
控制策略/控制器给定当前观测与目标，下一步发什么执行器指令Duck ONNX + BAM；H1FlatTerrainPolicy；Carter DifferentialController
OR 数学模型谁去哪个目标、走路还是搭车、何时占用支持机器人、优化什么成本Vehicle–H1 的方式选择、容量/同步与时序约束；扫地机–Duck–Stretch 仍须依据能力结果建模

关节角、摩擦系数不是任务分配变量；ONNX 网络不是 OR 求解器；机器人能站立也不意味着能完成换乘计划。OR 的时间/速度参数必须说明来自配置、测量还是假设。

XML、MJCF、URDF、USD

XML 是文本组织语法。MJCF 是 MuJoCo 的描述格式，通常以 <mujoco> 为根，包含身体、关节、惯性、碰撞、执行器等。URDF 也通常采用 XML，但以 <robot> 下的 link/joint 组织机器人。文件扩展名都是 .xml 不表示含义相同。USD 是 Isaac 场景/资产表示，不能因为机器人同名就替换成 MJCF。

在本地 Duck，scene.xml 包含 robot_groundcontact.xml 并增加静态地面；scene_ball.xml 还包含 ball.xml。把球加入世界会改变整个场景的状态长度。scene_allcollisions.xml 是另一碰撞版本，虽维度相同，也不能视为同一物理模型。

link 可以理解为一块刚体。MJCF 用嵌套 body 表达刚体树，geom 表示可视/碰撞形状；固定在一起的装饰部件不必增加自由度。joint 指定身体相对父身体允许怎样运动，actuator 才规定如何施力或跟踪目标。被动关节、联动关节、自由基座都可能没有独立执行器。

nq、nv、nu 与数组

课程符号中文理解本地读取
nq / qpos构型坐标的数量 / 当前构型数组model.nq / data.qpos
nv / qvel速度自由度的数量 / 当前广义速度数组model.nv / data.qvel
nu / ctrl执行器输入数量 / 当前控制输入数组model.nu / data.ctrl
njntjoint 元素数，不等于速度自由度model.njnt
mj_step用控制和外力推进一次动力学积分mujoco.mj_step(model, data)

一个 hinge 或 slide 贡献 1 qpos + 1 qvel；一个 ball joint 贡献 4 + 3；自由基座 free joint 贡献 7 + 6，其中位置占 3 项、单位四元数占 4 项。四元数的四个数不代表四个独立转动自由度。这解释了 Duck 的 nq=7+14=21、nv=6+14=20、nu=14。这里“14 个策略关节”也不等于“15 个 joint 元素”中的全部。

一个自由球新增 7 qpos + 6 qvel，不增加执行器；Duck 加球得到 28/26/14。v3 组合为 27+21+7+7=62 个构型坐标，26+20+6+6=58 个速度坐标，10+14=24 个输入。静态桌没有自由关节。等式约束会限制运动，却不直接删掉这些数组中的坐标；不能简单用 nv - neq 算“真正自由度”。

qpos/qvel 是机械状态的重要部分，不一定是恢复整台仿真的全部状态；还可能需要 actuator activation (act)、控制器记忆、接触求解和策略历史。Duck 的 61 维观测含上一动作和命令，既不是 nq，也不是 nq+nv。

坐标与控制的常见误读

各卡片以米、秒、弧度说明控制。MJCF body.pos 相对父身体，joint.axis 在该关节所属身体的局部坐标中解释。Duck 的多个 pitch/roll joint 在文件里都写局部 Z 轴：父/子身体的旋转不同，不能因此说它们都绕世界竖直轴转。完整父身体、局部位姿和轴保存在 inventory 的 bodies 与 joints。

自由关节 qpos 中的基座位姿与 body 局部位姿字段含义不同。MuJoCo 四元数采用 w,x,y,z，本地 Isaac 适配层也用 wxyz 提取朝向；接其他库时必须确认顺序。世界 XY 用于地面目标、Z 为高度；机器人身体坐标中的前向速度需经当前朝向转换到世界坐标。关节速度和自由体角速度不能靠将四元数逐项求导代替。官方计算说明

ctrl 不总是力矩：position actuator 通常接收位置目标，velocity actuator 接收速度目标，motor 的输入经 transmission/gear 转为广义力。Stretch 3 车轮通道用 rad/s，lift 用 m，腕部用 rad；arm 是伸缩腱目标，不能当某一节 slide 的位置。本地 Duck 的原 XML 是位置伺服路径，BAM 编译会在内存中换成 motor，再由 BAM 将关节目标转换成执行器输出。因此必须同时写明模型与控制配置。

对应一次控制循环

# 示意；不在本任务执行。targets 必须符合该具体 actuator 的语义。
model = mujoco.MjModel.from_xml_path(scene_path)
data = mujoco.MjData(model)
data.ctrl[:] = targets
mujoco.mj_step(model, data)

mj_step 推进物理，并不自动规划路线或调用某个 ONNX 策略。本地 Duck 每 0.02 s 更新策略，每个控制周期调用 4 次 0.005 s 的 mj_step；BAM 在各物理子步更新。一次模型加载或 mj_forward 都不是成功走了一步的证据。具体调用见 MicroDuck.step本地核验记录：MuJoCo/scripts/microduck_experiment.py。

Isaac 使用 articulation 状态 API 和物理步进，而非 MuJoCo 的这三个数组。课程对照应写“基座位姿/速度、关节状态、目标位置/轮速”，本轮未加载 USD 得到的实际完整维度标未知。
