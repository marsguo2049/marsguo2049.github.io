CarlaAir：读懂地面车辆与无人机

模型知识与来源，按需阅读。未发布的实验文件以“本地核验记录”标识；这些数值不构成实机规格。

CarlaAir 适合用“身体/载体 → 状态与坐标 → 控制接口 → 协作事件”来读。身体仍然重要，但这里先认道路车辆的 blueprint / actor 和 AirSim 的具名飞行器，再看它们接收什么任务命令；不把 MuJoCo 的关节数组生搬过来。

对照课程：哪些概念保留，哪些需要换一种问法

课程里的问法在 CarlaAir 中先看什么
XML / link / joint：身体怎么连接？车辆 blueprint、actor 实例、物理/碰撞体、轮胎和悬挂；无人机 pawn、机体与旋翼。仅凭画面不能统计完整关节。
qpos / qvel：在哪里、动多快？车辆 transform / velocity；无人机 kinematics_estimated 的位置、姿态与速度。名字和结构不同，但仍是在读状态。
ctrl：向哪里发命令？地面任务目标交给 Traffic Manager；飞行目标交给 AirSim 高层 API。底层控制器继续计算车辆控制或飞行器动作。
nq / nv / nu：表有多长？不适用这组 MuJoCo 模型字段。不能把 [x,y,z,speed] 的四个 API 参数叫做四个电机，也不能由“四旋翼”猜 nu=4。
mj_step：世界怎样推进？CARLA/AirSim 的引擎与同步设置推进物理；RPC 命令、轮询和任务事件不是同一个物理时间步。
多智能体怎样区分？地面 actor ID、逻辑 agent ID、vehicle_name 分开记录；给 Drone1 的命令不能省略名字而误发默认飞行器。

控制链与观察链

地面 V1B 适配器本地核验记录：CarlaAir/mission_execution/v1b_ground_adapter.py 将目标点变成 CARLA Location，启用 autopilot 并调用 TrafficManager.set_path。Traffic Manager 再驱动车辆；适配器停车时明确发送零油门、全制动和手刹。手动演示中的 VehicleControl(throttle, steer, brake) 是另一个接口层次，不能说 OR 求解器在逐帧计算方向盘。

空中 具名适配器本地核验记录：CarlaAir/mission_execution/v1b_drone_adapter.py 将任务目标作为 NED 坐标发送给 moveToPositionAsync，同时传速度与 vehicle_name，随后读取位置、速度、碰撞等状态并判断到达。它复用 SimpleFlight 的飞行控制；本地短航段速度上限处理不等于新开发了飞控策略。

这两条链都有物理运动，但初始化中的 simSetVehiclePose 属于摆放/恢复，不能计为飞行；相机画面能收到也不意味着它参与了导航。双机相机配置本地核验记录：CarlaAir/AirSimConfig/settings.stage2_v1b_2drones.json 声明 bottom_center、640×480、90° FOV、向下俯视。配置分辨率、实际收帧、识别目标、根据识别结果闭环控制，是四件不同的事。

最容易踩坑的是坐标与时间

CARLA API 的位置单位为米、欧拉角为度，采用 X 前、Y 右、Z 上的左手坐标约定；AirSim API 使用米制 NED，Z 向下。参考 CARLA 坐标文档 与 AirSim API 坐标说明，查阅于 2026-09-05；这些说明不替代本机打包版本核验。

本地 DroneFollower.calibrate本地核验记录：CarlaAir/examples/demo_drive_and_fly.py 对轴向已经对齐的两个世界建立偏移：

x_air =  x_carla + ox
y_air =  y_carla + oy
z_air = -z_carla + oz

假设标定所得 oz=2 m，CARLA 中高度 z=12 m 对应 AirSim z=-10 m。这是帮助理解的算例，不是某次运行的标定值。换了地图原点、出生点或引擎轴向，应重核标定；若轴向还有旋转，就不能继续只用这三个偏移量。姿态、速度向量、角度单位也须各自转换，不能只转换目标位置。

对会合而言，还要区分仿真时间、墙钟时间、命令派发时间、观测时间与事件时间。moveToPositionAsync 返回不等于无人机已经到达；一张旧图也不能证明“现在 READY”。要有实际位置/速度、稳定保持与新鲜观测，才可生成相应会合事件。

已经证明到哪一步

固定证据 dual_sync_retry_acceptance.json本地核验记录：CarlaAir/experiments/autonomous_or_v0_6a/transfer_sync/dual_sync_retry_acceptance.json 接受的是 Sprinter–Drone1 的并发移动、先到等待、双端 READY 与同步；它明确排除 HANDOFF、custody 变更、delivery 以及故障恢复，也不代表整个 v0.6a 验收完成。图中使用的是稍后的同步演示原帧本地核验记录：CarlaAir/experiments/autonomous_or_v0_6a/sync_demo/20260902T153849246615Z/run_01/frames/both_ready.png，保留原图的 presentation-only 标注；画面用于说明，验收结论追到 JSON。

按 组件当前入口本地核验记录：CarlaAir/README.md，inspection 仍是逻辑计时服务，路径/任务使用仿真真值，不宣称视觉巡检；cargo/custody 是逻辑合同，不等于实物装卸。平台具名 2G2A 接入也不自动证明多 worker 的 OR 调度闭环。

这里的三种“模型”也要分开：车辆/飞行器描述及物理参数决定能怎样运动；Traffic Manager / SimpleFlight负责实际控制；OR 数学模型安排任务分配、路径选择和同步约束。当前 CarlaAir 并发执行器来自本地 autonomous_or_adapter/runtime_v0_6a.py，它的历史 live 成果不能直接算作共享 Execution 执行器验收。
